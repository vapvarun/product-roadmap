# Product Roadmap 1.7.0 — Automated Implementation & Release Pipeline

**Goal:** drive all 12 fix workstreams from code → test → verified-against-site-owner-expectation → release, with **fail-closed gates** and minimal manual steps. One pipeline, both plugins, branch `1.7.0`.

**Reads:** `plan/1.7.0-fix-plan.md` (what to build), `plan/1.7.0-browser-test-checklist.md` (how to verify in browser), `plan/1.7.0-acceptance-criteria.md` (site-owner expectation gate).

**Core rule:** a workstream is DONE only when its static + functional + browser gates pass. The acceptance-criteria gate (`1.7.0-acceptance.json`) re-runs after every workstream — no drift, no "green in isolation, broken together."

---

## Pipeline shape (deterministic orchestration)

```
Stage 0  BASELINE        seed data · snapshot current fail-state (wppqa + funct-gate + acceptance.json)
   │
Stage 1  IMPLEMENT       per workstream, dependency-ordered; paired free+pro edited together
   │   (W1→W2→W3) (W6→W7) (W5) (W8) (W9) (W10) (W11)
   │        each workstream immediately runs its own gate chain ▼
   ├─ 1a STATIC GATE     php -l · WPCS · PHPStan · contract-audit · enum · rest-js-contract
   ├─ 1b FUNCTIONAL GATE  wp eval-file funct-gate.php (internal REST asserts) · dead-hook count == 0
   ├─ 1c BROWSER GATE     Playwright per BT-<ws> item · 3 viewports · light/dark · roles · screenshots
   └─ 1d ACCEPTANCE       re-run acceptance.json → the rows this workstream owns flip green
   │
Stage 2  SCALE GATE      seed 1000+ · time hot paths + export vs budgets (S1-S6)
Stage 3  ACCEPTANCE FULL  every MUST row green on seed AND clean-install pass
Stage 4  CLEANUP          phpcbf (W12) · teardown seed · re-run CI
Stage 5  RELEASE          W4 version bump + changelog · build-release.sh · Docker pristine install · tag · gh release · Slack
```

Fail-closed: any gate red → pipeline halts, names the owning workstream + failing acceptance ID, leaves branch in a known state. No stage proceeds on a red MUST.

## Parallelism & pairing
- **Sequential (shared surface):** W1 → W2 → W3 (all touch the free↔pro hook/product contract). W6 → W7.
- **Parallel (independent, worktree-isolated):** W5, W8, W9, W10, W11 can run concurrently after Phase A lands.
- **Paired free+pro (edit + test together, both active):** W1, W3, W8, W9, W10.
- **Last:** W12 (phpcbf, after all hand edits) → W4 (bump + tag).

## Automation harness to build (Stage 0 prerequisites)
1. `bin/funct-gate.php` — asserting version of `scratchpad/funct-test.php`; exits non-zero on any core-flow failure or dead-hook>0. (Free, reused by pipeline.)
2. `plan/1.7.0-acceptance.json` — the acceptance matrix as data (IDs → check type → threshold).
3. `bin/acceptance-run.sh` — runs each acceptance check (REST/DB/grep/Playwright-driver) → writes pass/fail JSON; exit 1 on any MUST red.
4. `scratchpad/seed.php` + teardown (exists).
5. Playwright driver list keyed to BT-* IDs.

These make the flow re-runnable and CI-gateable (drop `acceptance-run.sh` into `build-release.sh` as a release gate, like the QA-coverage gate).

## How it runs
Two options (your call):
- **A. Multi-agent Workflow** (recommended for full run): one Workflow script executes Stages 0-5, fanning out implement+verify per workstream via `pipeline()`, fail-closed on gates. Billable/opt-in. I author `1.7.0-release.workflow.js`, you approve, it runs end-to-end and reports per-gate.
- **B. Phased manual** (tighter control): I run Phase A (W1-W3) with its gates, show you green acceptance rows P1/P2/P4, then continue. Same gates, human checkpoint between phases.

Either way the gates and acceptance criteria are identical — the pipeline just automates the loop.

## Release trigger
GO when `acceptance-run.sh` = all MUST green on seed + clean install, CI green, versions consistent → `/wp-plugin-release` builds, Docker-installs, tags `v1.7.0` on both, publishes, notifies #ready-for-release.
