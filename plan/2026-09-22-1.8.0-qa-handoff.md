## 1. Read this first: test on an UPGRADED site

Several fixes only exist on the upgrade path. A fresh install has always worked — that is
precisely why these bugs survived QA for months. **Testing a clean activate will not
exercise them.**

To simulate an upgraded site on a local install:

```
wp option update roadmap_version 1.6.0
wp option delete roadmap_pro_version
```

Then load any front-end page once. That triggers both migrations. Verify:

```
wp eval 'global $wpdb; print_r($wpdb->get_col("SHOW COLUMNS FROM {$wpdb->prefix}roadmap_votes"));'
```

Expect `guest_ip` and `user_agent` present. If they are missing, the migration did not run
and everything in section 3 will fail for the wrong reason.

## 2. What changed, in one paragraph

This release is mostly **security and data integrity**, not features. Five REST routes were
authorising with a site-wide capability instead of a per-object check; neither plugin could
migrate an existing install, so schema and defaults added since 1.0 never reached anyone who
upgraded; guest voting was blocked in four places at once; saving one Settings tab silently
reset the other; and ten of eleven Pro options rendered on no screen at all. Vote counts now
mean "number of voters" rather than a net score, which **changes displayed numbers on
upgrade**.

## 4. Expected changes that are NOT bugs

Please do not bounce these:

1. **Vote counts go up.** On any board that has received a downvote, numbers increase once on
   upgrade. The stored value was a net score; it is now a count of voters. This is in the
   changelog.
2. **`/items/<id>` is roadmap-items-only, for everyone.** An administrator deleting a Page
   through that route now gets 403. Managing other post types was never the intent.
3. **Radio and email field types still render nowhere.** The handlers exist; no current screen
   uses them. Two cards about this were closed on that basis.
4. **Filters now cause a network request.** They were client-side and wrong; they are now
   server-side and correct. Expect a brief load rather than instant re-filtering.
5. **Removed settings.** API key, Enable REST API, Enable Export, Enable Analytics, Enable
   Custom Fields, Export Permission roles, Allow users to switch templates, Default Template
   (duplicate key). All were read by nothing.

## 6. How this was verified so far

Everything below was checked at the REST and database layer, and **none of it involved a
browser**. That is the gap this handoff exists to close.

- PHPStan clean on every changed file in both plugins
- Plugin Check run against the **built zip**, not the working tree
- Per-role REST checks: anonymous, subscriber ×2, contributor, editor, administrator
- Migration verified by breaking an install and repairing it with one front-end request
- Query counts measured on 1013 items (board: 311 → 86 queries per 100 items)

**Lesson worth carrying:** minification renames every bound local, so a long identifier
surviving unminified at a call site in `roadmap-app.js` means it resolved to a global that
does not exist. Grepping the built bundle for `await [a-zA-Z]{4,}(` is a cheap release check
that would have caught the board outage without a browser.
